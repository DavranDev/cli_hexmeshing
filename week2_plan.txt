T1. SELF-CONTAINED DOCKERFILE  (Wed PM -> Thu)
--------------------------------------------------------------------------------
GOAL: `docker build` produces an image that already contains the compiled
`hex` + evocube binaries built from the cli-runner source — no host-mounted
source, no manual compile.sh step. (Today: env-only Dockerfile + run_docker.sh
mounts + compile.sh by hand.)

DESIGN DECISIONS (made up front):
  - COPY the source from the build context rather than `git clone` inside the
    build. Reason: the forks may need auth (NEVER bake the token into a layer),
    and COPY guarantees the image matches the checked-out commit being tested.
    Document the alternative (clone of public repo) in a comment.
  - Reuse the already-downloaded libtorch zip + vulkan SDK tarball from the
    repo root via COPY (they're already next to the Dockerfile; setup.sh put
    them there). Avoids re-downloading ~3 GB per build; keep the wget lines
    as a documented fallback path.
  - Two-stage build: `builder` (cuda devel image, compiles) -> `runtime`
    (same cuda base, copies binaries + libtorch/vulkan runtime libs + assets).
    If the runtime-slimming fights back, shipping the single-stage devel image
    is an acceptable Friday fallback — note it and move on.
  - GPU is NOT needed at build time (nvcc compiles without a device); GPU + X11
    are needed only at `docker run` time. State this explicitly in the docs.

STEPS:
[ ] 1.1  Write .dockerignore: output/, */build/, *.zip, *.tar.xz (except the
         two library archives if COPYing them — better: COPY them explicitly
         and ignore everything not needed), .git of submodule optional,
         github_token.txt (mandatory), data/.
[ ] 1.2  Verify the build context is sane: `docker build` context size should
         be source + the two library archives, not 10+ GB. Check with
         `du -sh` after .dockerignore.
[ ] 1.3  Write Dockerfile.build (keep the existing env-only Dockerfile
         untouched so run_docker.sh keeps working):
         Stage "builder":
           FROM nvcr.io/nvidia/cuda:12.4.1-cudnn-devel-ubuntu22.04
           - apt deps: copy the list from the current Dockerfile (git cmake
             build-essential python3 blas/lapack GL/X11 dev libs, libhdf5,
             vulkan-tools) — keep versions identical to the proven image.
           - COPY + unzip libtorch -> /space/lib/libtorch
           - COPY + untar vulkan SDK -> /space/lib/vulkan-sdk-1.3.268.0
           - COPY evocube/ interactive-hex-meshing/ compile.sh -> /space/...
           - RUN bash /space/compile.sh   (it already does: evocube cmake+make,
             source vulkan setup-env.sh, hex cmake -DCMAKE_BUILD_TYPE=Release
             -DTorch_DIR=..., make -j8)
         Stage "runtime":
           FROM nvcr.io/nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04 (try;

[ ] 1.4  Build it: `docker build -f Dockerfile.build -t hexmesh-cli:week2 .`
         Record wall time + image sizes (goes in the report).

T2. HEADLESS FEASIBILITY MEMO  (Thu -> Fri AM; prototype only if cheap)
--------------------------------------------------------------------------------
GOAL: a memo (cli_run/HEADLESS.md) that says exactly what stands between
"--exit-after GUI automation" and a true `--headless` mode, with an effort
estimate Ronald can make decisions from. Prototype only if the trace shows
it's a few guards.

WHAT WE ALREADY KNOW (verified in source, cite in memo):
  - main.cpp:27-28 — HexMeshingApp is constructed and app.Prepare() runs
    BEFORE the script branch; Prepare() -> Application::Prepare() (vkoo) is
    where the Vulkan instance/window/swapchain/GUI come from
    (HexMeshingApp.cpp:38-49: CreateSampler, SetupScene,
    SetupRenderPipelines, vkoo::Gui).
  - The script path SKIPS MainLoop() when --exit-after is set, so per-frame
    rendering is already absent; the window only exists because Prepare()
    made it.
  - Stage code touches views at a finite, known set of call sites:
      DeformationStage.cpp:136,169  -> UpdateDeformationViews() (:208)
      DecompositionStage.cpp:300 (UpdatePolycubeView), :462 (UpdateAnchorsView)
      DiscretizationStage.cpp:110,121,283 (UpdatePolycubeComplexView),
        :175-274 (pending_view_ HexCollectionView lifecycle)
      HexahedralizationStage.cpp:33-70 (OnEnter creates LandmarksEditingView /
        QuadSurfaceView), :293,:522,:556-558 (UpdateFilteredMeshView), plus
        mouse-interaction sites (:808-913) that never run headless anyway.

STEPS:
[ ] 2.1  Trace vkoo::Application (vkoo/ dir): constructor + Prepare().
         Enumerate exactly what gets created: glfwInit/glfwCreateWindow,
         VkInstance, VkSurfaceKHR, device, swapchain, render pipelines, Gui.
         Note which of these the COMPUTE path actually needs (expected: none —
         the optimizers are libtorch/CUDA, see T3 — but verify whether models/
         views allocate GPU buffers through the vkoo device at load time).
[ ] 2.2  Classify every view call site above into:
           (a) pure display update, safe to skip when headless;
           (b) does real work as a side effect (like the Stage-1 polycube
               writeback bug we already found — HIGH ALERT for more of these,
               especially DiscretizationStage's pending_view_ block :175-274,
               which looks like it participates in hex accumulation);
           (c) only reachable via mouse/UI events (ignore).
         This classification IS the core of the memo.
[ ] 2.3  CHEAP EXPERIMENT — xvfb-run (30-60 min, do early, inside the T1
         image or the old one): apt install xvfb;
           xvfb-run -s "-screen 0 1280x720x24" ./cli_run/smoke_test.sh
         Outcomes either way are reportable:
           PASS -> "runs on a headless server with a virtual display TODAY"
                   (unblocks CI/server use before true headless exists).
           FAIL -> record the error; likely NVIDIA Vulkan ICD vs Xvfb (no GLX);
                   note workarounds (EGL/offscreen surface) in the memo.
[ ] 2.4  Decide the recommended mechanism and estimate effort. Candidate
         designs, in increasing depth:
           A. `--headless` flag: skip Prepare()'s window/GUI/scene setup,
              guard the (a)-class view calls (null GlobalView or if-guards),
              re-route any (b)-class side effects into stage logic the way the
              Stage-1 fix did. Estimate per-file touch count from 2.2.
           B. Vulkan-without-surface (VK_KHR_display-free headless instance) if

           C. xvfb-run documented as the operational stopgap regardless.
[ ] 2.5  If 2.2 found ZERO (b)-class sites outside what's already fixed and

         run smoke test, report metrics diff vs GUI run (must be identical /

[ ] 2.6  Write cli_run/HEADLESS.md: findings, call-site table, xvfb result,
