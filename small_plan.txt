------------------------------------------------------------
4B. GPU / Vulkan / CUDA split (PRELIMINARY — to verify in Weeks 2-3)
------------------------------------------------------------
Two SEPARATE dependencies, often conflated:
  * VULKAN + X11/display  -> used ONLY to render the GUI window. The pipeline
    computation does NOT use Vulkan. This is what a headless mode would remove.
  * CUDA / NVIDIA         -> used for the actual MATH: libtorch (CUDA tensors,
    Adam, autograd/backward) + geomlib custom .cu kernels. This is what a
    CPU-only mode would have to replace.

Per-stage, preliminary (CONFIRM by tracing in Week 2):
  Stage 0 deform        : libtorch CUDA (volumetric deformation optimizer).  GPU.
  Stage 1 decompose     : geomlib CUDA kernels (SDF: PointTetMeshTest,
                          GeneralizedTriangleProjection) + libtorch CUDA
                          (PolycubeOptimizer Adam/backward).                 GPU.
  Stage 2 discretize    : appears largely combinatorial (regular grid + quad
                          extraction) — strongest CPU-only candidate.        VERIFY.
  Stage 3 hexahedralize : libtorch CUDA + geomlib projection (HexComplexDeformer). GPU.

Implication: a headless (no-Vulkan) mode looks more tractable than a CPU-only
(no-CUDA) mode. Recommend tackling headless first (Vulkan is display-only), then
scope CPU-only per stage (Stage 2 first).

5. RISKS / OPEN QUESTIONS / DECISIONS NEEDED
================================================================================
- PUSH: latest work is committed locally only. Need go-ahead to push `cli-runner`
  to both forks so reviewers can pull. (Required before Friday.)
- BINARY PORTABILITY: the prebuilt `hex` only runs on a matching environment
  (CUDA 12.4 + matching driver + libtorch + Vulkan). "Same system environment"
  must be confirmed, else reviewers fall back to the Docker build.
- NATIVE BUILD: fully documenting/verifying a non-Docker build is the riskiest
  Week-2 item without a clean test machine; may slip to a "best-effort + known
  gaps" doc.
- TRUE HEADLESS: may need a non-trivial refactor of app startup + guarding the
  view/GUI calls inside stages. Week 2 delivers feasibility; Week 3 delivers
  impl-or-design accordingly.
- CPU-ONLY: geomlib ships CUDA-only kernels; a full CPU path is a larger effort.
  Likely outcome is "Stage 2 CPU-capable + a costed plan for the rest", not a
  full CPU pipeline in 3 weeks.
